## Analysis

### What Changed Between Runs

The code is identical. The difference is force-merge: this run merged all segments into 1 before the search phase. The previous run had 260 segments with lazy SORTED_SET decode causing cold-start spikes on first access per segment.

### Remaining Issues

1. **hourly_agg_with_filter +66% P50, +80% P90**: This is the primary remaining regression. The filter aggregation scans timestamp ranges and computes hourly buckets — it exercises the V6 flat packed timestamp field heavily. The global bpv (33 bits) vs per-block bpv (23 bits) trade-off amplifies full-scan cost.

2. **hourly_agg_with_filter_and_metrics +70% P50, +77% P90**: Same root cause as above, compounded by additional metric aggregations.

3. **range +10.8% P50**: Borderline fail. Within noise range — was +23.7% in previous run.

4. **status-400s-in-range +50% P90**: Selective filter on rare status codes (400s) with range constraint. The P50 is fine (+3.8%), suggesting P90 spike is from occasional segment-level decode overhead.

### Conclusions

- Force-merge eliminates the P90 cold-start problem entirely (1/15 → 12/15 PASS)
- The 3 remaining failures are all timestamp-heavy aggregation queries affected by V6 global bpv trade-off
- Sort operations are now consistently faster than baseline (desc_sort_size -43%, asc_sort_size -36%)
- search_after queries are dramatically faster (desc_sort_with_after -30%, asc_sort_with_after -43%)
- Next optimization target: per-field bpv strategy for monotonic timestamp fields, or hybrid block/flat format
