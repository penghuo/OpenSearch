# Benchmark: reading `flat_object` values from `_source` vs from a Variant blob column

**Date:** 2026-08-26 01:00

This is a self-contained report. It defines both configurations under test, the corpus, and every query, then gives the
results. No knowledge of earlier benchmark rounds is assumed.

---

## 1. The question

A `flat_object` field indexes arbitrary JSON without a mapping. It writes terms that support *filtering* on subfields, but
nothing that supports *retrieving* a subfield's value — so to aggregate over one, a script has to read the value back out of
`_source`.

This measures the cost of that, against the cost of reading the same value out of a pair of doc-values columns.

| | how the aggregation gets the value |
|---|---|
| **solution A** | a Painless script reads `params._source.attributes` — the current, only way |
| **variant-enc** | a Painless script reads a Variant-encoded blob held in doc-values columns |

Everything else is held identical: same documents, same mapping for the `flat_object` field's terms, same derived-field
names and types, same query bodies. The only difference is which store the script reads.

---

## 2. The two configurations, exactly

### 2.1 solution A — read from `_source`

```json
{
  "settings": { "index": {
      "number_of_shards": 1, "number_of_replicas": 0,
      "refresh_interval": "-1", "translog": { "durability": "async" } } },
  "mappings": {
    "dynamic": false,
    "properties": {
      "@timestamp":  { "type": "date" },
      "attributes":  { "type": "flat_object" }
    },
    "derived": {
      "attr_status":    { "type": "long",    "script": { "lang": "painless", "source":
        "def a = params._source.attributes; if (a != null) { def x = a['status']; if (x != null && x instanceof Number) { emit(((Number)x).longValue()); } }" } },
      "attr_namespace": { "type": "keyword", "script": { "lang": "painless", "source":
        "def a = params._source.attributes; if (a != null) { def x = a['k8s.namespace']; if (x != null) { emit(String.valueOf(x)); } }" } },
      "attr_sparse":    { "type": "long",    "script": { "lang": "painless", "source":
        "def a = params._source.attributes; if (a != null) { def x = a['process.runtime.name']; if (x != null && x instanceof Number) { emit(((Number)x).longValue()); } }" } },
      "attr_rare":      { "type": "long",    "script": { "lang": "painless", "source":
        "def a = params._source.attributes; if (a != null) { def x = a['custom.tenant.attr_248']; if (x != null && x instanceof Number) { emit(((Number)x).longValue()); } }" } }
    }
  }
}
```

`_source` is enabled and complete, which is the default. Per document the script forces a stored-fields block to be
decompressed and the whole document parsed into a `Map`, then reads one entry from it.

This is **not a strawman**: it is what `SourceLookup` and derived fields do today, and there is no other way to aggregate a
`flat_object` subfield. Optimising it — a lazier `_source` reader, for instance — is separate work and is not attempted
here. It is the status quo, measured as it is.

### 2.2 variant-enc — read from doc-values columns

Identical, except for two lines:

```json
  "_source": { "excludes": ["attributes"] },
  "properties": {
      "attributes": { "type": "flat_object", "variant_blob": true }
  }
```

and the scripts read the column instead of `_source`:

```
def v = variant('attributes'); if (v != null) { def x = v.getLong('status'); if (x != null) { emit(x); } }
```

`variant_blob` makes the mapper additionally write the field's value as two doc-values columns:

- `attributes._blobnames` — `SORTED_SET`: every distinct key name in the segment, stored once, plus each document's names
  as a list of ordinals into that dictionary.
- `attributes._blob` — `BINARY`: the document's value tree in the Apache Parquet Variant binary encoding, with field ids
  ordered so that field id *i* is the document's *i*-th smallest key name — which is exactly what the ordinal list gives.

Excluding `attributes` from `_source` is what makes this a fair storage comparison rather than a double charge: once the
value is in a type-preserving column, keeping a second copy as text inside `_source` is redundant. The other fields stay in
`_source` normally.

**The terms are identical in both configurations.** `variant_blob` adds no terms, so `attributes`, `attributes._value` and
`attributes._valueAndPath` — and therefore all filtering — are byte-identical. Section 6.1 uses that as a control.

## 3. The test set

`SVC_10K`, generated by `OtelDocGenerator`, deterministic in its seed. It models 10,000 services emitting
OpenTelemetry-shaped log records, where each service always emits the same attribute keys and **most of those keys belong to
that service alone**.

```
per document    4 stable keys        status, duration_ns, level, k8s.namespace   (present in every document)
              + ~20 shared keys      drawn from a 1,000-name pool of real OTel semantic-convention names,
                                     sampled by Zipf rank so a few are common and the tail is rare
              + 76 private keys      owned by that one service; no other service emits them
              = ~100 attributes

whole corpus    1,000,000 documents, each assigned a service by Zipf weight
                vocabulary = 1,000 shared + 10,000 x 76 private = ~761,000 distinct key names
```

Values are a fixed mix: 40% string, 25% integer, 15% double, 8% boolean, 4% null, 4% array, 4% nested object (each nested
object carrying 2–3 fields). So the corpus exercises type fidelity and nesting, not just flat scalars.

Measured from the finished index rather than taken from the configuration:

| | measured |
|---|---|
| documents | 1,000,000 |
| distinct key names per document | **99.46** (min 89, max 107) |
| **distinct key names in the segment** | **761,007** |
| total name references | 99,460,979 |
| `attributes` JSON per document | 2,785 B |
| whole document | 2,846 B |
| raw corpus | 2.85 GB |

Two properties of this corpus matter for reading the results:

- **Documents are wide** (~100 attributes). Since solution A parses the whole document to read one field, width is the
  variable its cost tracks.
- **The vocabulary is large** (761,007 names), because services own their key names. That is what real telemetry looks like
  when services emit custom attributes, and it is the variable the blob column's *memory* cost tracks.

**Why 1,000,000 documents and not more:** solution A needs 235 s for a single iteration of the group-by query on this
corpus. Ten million documents would have put one configuration's query set into the tens of hours.

### 3.1 A second, narrower corpus, used for one comparison

Section 6.2 refers to a second corpus to show how the results move with document width. Defined here so that section reads
without going elsewhere: same generator and same value mix, but **~16 attributes per document**, all drawn from a shared
1,000-name pool with no per-service private names — so its vocabulary is **1,007 names** — at 10,000,000 documents. Its
`attributes` JSON is 441.5 B/doc against this corpus's 2,785 B.

## 4. The query set

Eleven queries, fixed and numbered. **Both configurations receive byte-identical request bodies** — the only difference is
the script inside the derived field each query names, which is what makes the difference attributable to the value store.

Scoping is a `range` inside the `query` clause, not a `post_filter`, because a post filter runs *after* aggregation and would
leave an aggregation scanning the whole corpus while appearing to scope it.

| Q | body | docs scanned | what it is for |
|---|---|---|---|
| Q1 | `{"size":0,"aggs":{"total":{"sum":{"field":"attr_status"}}}}` | 1,000,000 | baseline: read one always-present value, full scale |
| Q2 | Q1 + `"query":{"range":{"@timestamp":{"lt":…}}}` at 10% | 100,000 | same read, scoped |
| Q3 | same at 1% | 10,000 | same read, scoped further |
| Q4 | `{"size":0,"aggs":{"by_ns":{"terms":{"field":"attr_namespace","size":32},"aggs":{"total":{"sum":{"field":"attr_status"}}}}}}` | 1,000,000 | grouped aggregation reading **two** paths per document |
| Q5 | Q4 scoped to 10% | 100,000 | the grouped shape, scoped |
| Q6 | `{"size":0,"aggs":{"total":{"sum":{"field":"attr_sparse"}}}}` | 1,000,000 | path present in only **13.21%** of documents |
| Q7 | `{"size":0,"aggs":{"total":{"sum":{"field":"attr_rare"}}}}` | 1,000,000 | path present in only **1.30%** of documents |
| Q8 | `sum` + `avg` + `min` + `max` + `value_count`, all on `attr_status` | 1,000,000 | do five aggregations on one path cost one read or five? |
| Q9 | `sum` on `attr_status` **and** `sum` on `attr_sparse` | 1,000,000 | marginal cost of a second path |
| Q10 | `{"size":50,"query":{"term":{"attributes":"info"}},"fields":["attr_status"]}` | 50 | **expected to favour `_source`**: the document is loaded for the hits anyway |
| Q11 | `{"size":0,"query":{"term":{"attributes":"info"}},"track_total_hits":true}` | 1,000,000 | **control.** Touches only the shared terms, so it must show no difference |

The paths behind the derived fields: `attr_status` → `status`, `attr_namespace` → `k8s.namespace`,
`attr_sparse` → `process.runtime.name`, `attr_rare` → `custom.tenant.attr_248`.

Q10 and Q11 are included precisely because they are the cases where the blob should *not* win. Q11 must show no difference
or the experiment is broken; Q10 pays the blob's setup cost with only 50 documents to amortise it over.

## 5. Method

- **Host:** 16 vCPU, 61 GiB RAM, NVMe. OpenSearch 3.6.0-SNAPSHOT, Lucene 10.5.0, 16 GiB heap.
- **Index:** 1 shard, 0 replicas, force-merged to a single segment, verified segment count = 1 before reading.
- **Indexing:** 8 client threads, 2,000-document bulks, refresh disabled during bulk. Throughput is measured over a steady
  window that excludes the first 100,000 documents.
- **Storage:** read from the on-disk files after polling until the store size stops changing, because immediately after a
  force merge the merged-away segments can still be present and would double the reading.
- **Queries:** `request_cache=false`, **n=5** timed iterations after 2 warmups, server-side `took`, p50 and p90.
- **A fresh JVM per configuration** for the query phase, so one configuration's GC state cannot be charged to the other.
- **Concurrent segment search is on** (`mode=auto`, the default), so a query is partitioned within the single segment. Both
  configurations get it equally.

**n=5 rather than 10** because solution A's Q4 is 235 s per iteration; ten timed iterations plus warmups was hours. The
effects here are 40–200×, which n=5 resolves easily, but it makes p90 the 5th of 5 values rather than a real tail estimate.

**One run was discarded.** The first query phase was contaminated by my own `gradle test` running concurrently, which
inflated solution A by 5–15%. Everything below is a re-run on an idle machine with the Gradle daemons stopped.

## 6. Results

### 6.1 Storage

Bytes per document, from the single force-merged segment.

| file | what it is | solution A | variant-enc | delta |
|---|---|---|---|---|
| **total** | | **5,338.59** | **5,228.27** | **−110.32 (−2.07%)** |
| `.fdt` | `_source`, compressed | 1,584.38 | 13.77 | **−1,570.61** |
| `.dvd` | doc-values | 2,136.30 | 3,596.30 | **+1,460.00** |
| `.tim` | term dictionary | 1,384.94 | 1,385.05 | +0.11 |
| `.doc` | postings | 200.28 | 200.28 | +0.00 |
| `.tip` | terms index | 26.13 | 26.13 | +0.00 |
| `.kdd` | BKD tree (`@timestamp`) | 6.43 | 6.71 | +0.28 |

`.tim`, `.doc` and `.tip` agree to within 0.008%. That is the **control on this table**: both configurations write identical
terms, so had those files diverged the two would not be comparable.

**The trade is explicit:** give up 1,570.61 B/doc of `_source`, pay 1,460.00 B/doc of doc-values columns. The blob is 93% the
size of the `_source` text it replaces, so the index is smaller — by 2.07%.

**Why the margin is small.** The cost *both* configurations pay dominates the index:

```
shared by both       3,754 B/doc      .tim + .doc + attributes._value + attributes._valueAndPath
_source text (A)     1,571 B/doc
blob columns (V)     1,460 B/doc
```

`.tim` alone is 1,384.94 B/doc, the largest file in the index. With per-service attribute names, `_valueAndPath` produces
~99 terms per document that are nearly all unique across the corpus, so its term dictionary is enormous. **Those columns
exist only for filtering and both configurations carry them in full.** A deployment that needs columnar value access but not
term-filtering on values could drop them and save several times what this whole change saves — that is the largest single
lever in a `flat_object` index, and it is a functional trade-off rather than an encoding one.

**Where the 1,460 B/doc of blob goes:**

| component | B/doc | basis |
|---|---|---|
| value tree | ~1,207 | 99.46 members × ~12.1 B — 1 B field id, 2 B offset, ~9 B value |
| per-document name ordinals | ~249 | 99.46 ords × 20 bits (`bitsRequired(761,006)`) |
| name dictionary, amortised | ~4 | 761,007 names, prefix-shared and LZ4-compressed, over 1M documents |

The names themselves cost ~4 B/doc because they are stored **once per segment**. The per-document part is just the ordinals.

### 6.2 Query latency

Server-side `took`, milliseconds, p50, n=5.

| Q | query | solution A | **variant-enc** | speedup | A p90 | V p90 |
|---|---|---|---|---|---|---|
| Q1 | sum, dense path, 1M docs | 36,736 | **178** | **206×** | 37,077 | 203 |
| Q2 | sum, dense path, 10% | 11,109 | **79** | **141×** | 11,315 | 84 |
| Q3 | sum, dense path, 1% | 1,095 | **25** | **44×** | 1,122 | 25 |
| Q4 | terms + sum group-by, 1M docs | 234,574 | **1,276** | **184×** | 235,713 | 1,315 |
| Q5 | terms + sum group-by, 10% | 22,799 | **147** | **155×** | 23,396 | 158 |
| Q6 | sum, sparse path (13.21%) | 36,821 | **177** | **208×** | 36,903 | 178 |
| Q7 | sum, rare path (1.30%) | 37,079 | **188** | **197×** | 37,561 | 205 |
| Q8 | five metrics, one path | 37,328 | **363** | **103×** | 37,648 | 406 |
| Q9 | sum on two paths | 36,896 | **262** | **141×** | 37,289 | 347 |
| Q10 | fetch top 50 documents | **6** | 17 | **0.4×** | 13 | 20 |
| Q11 | filter only — *control* | 1 | 1 | — | 1 | 1 |
| | **sum of all eleven** | **454,444** | **2,713** | **167×** | | |

**Q11, the control, behaves.** Both at 1 ms: the blob adds no terms, so a query touching no derived field is unaffected. Had
this differed, nothing else in the table would be trustworthy.

**Q10 is a loss, and an expected one.** Fetching 50 documents is 6 ms from `_source` and 17 ms from the blob. Section 6.5
gives the cause: binding the blob to this segment costs 21.62 ms, and a 50-document query has nothing to amortise it over.

#### How this moves with document width

The same query on the narrower corpus of §3.1 (~16 attributes/doc, 1,007 names), expressed per document so the two scales
are comparable:

| | ~16 attributes/doc | ~100 attributes/doc | change |
|---|---|---|---|
| solution A, Q1 | 1.31 µs/doc | **36.7 µs/doc** | **28× worse** |
| variant-enc, Q1 | 0.077 µs/doc | **0.178 µs/doc** | **2.3× worse** |
| speedup | 17× | **206×** | |

This is the shape of the whole result. Solution A parses the document to read one field, so its cost tracks document size;
variant-enc reads one path, so its cost tracks the path. **6.2× more attributes cost solution A 28× and variant-enc 2.3×.**

Solution A's 28× is superlinear in document size and **only partly attributed**: `.fdt` grew 6.5× per document and the
`attributes` JSON grew 6.3× (441.5 → 2,785.4 B), which accounts for ~6.5× of it. The remaining ~4× is not established. It is
not GC *pauses* — those are under 1% of query time (§6.4).

#### Selective queries make `_source` worse per document, not better

| | docs scanned | solution A | per doc |
|---|---|---|---|
| Q1, sequential | 1,000,000 | 36,736 ms | **36.7 µs** |
| Q2, filtered to 10% | 100,000 | 11,109 ms | **111.1 µs** |
| Q3, filtered to 1% | 10,000 | 1,095 ms | **109.5 µs** |

A stored-fields block holds only ~6 of these 2,846-byte documents, so a filter matching 1% of the corpus decompresses close
to a whole block per matching document, where a sequential scan spreads one block across six. **The narrower the filter, the
worse `_source` gets per document** — 3× here. variant-enc does not have this shape, because doc-values are addressed per
document and neighbouring documents share nothing.

### 6.3 Ingestion

| | solution A | variant-enc |
|---|---|---|
| throughput, steady window | 3,914.06 docs/s | **3,973.84 docs/s** (+1.5%) |
| bulk p50 | 1,303.98 ms | 1,848.98 ms |
| bulk p99 | 27,157.52 ms | 21,320.23 ms |
| force merge to one segment | 260.09 s | **420.11 s** (+61%) |
| young GC during indexing | 100 collections, 2,089 ms | 139 collections, 2,975 ms |

**Throughput is not distinguishable.** +1.5% is well inside the run-to-run spread this harness shows — repeated runs of the
same configuration have varied 11–19% — and bulk p50 and p99 disagree on which configuration is ahead.

Two costs that are real and are not throughput:

- **Force merge is 61% longer.** Merging two extra doc-values columns is work: the name dictionary has 761,007 entries to
  union and remap.
- **Indexing allocates more** (2,975 vs 2,089 ms of GC) — encoding the Variant and ordering its field ids. It does not
  surface in throughput because indexing here is bound elsewhere.

### 6.4 Memory and GC

Allocation measured with `ThreadMXBean` counters rather than heap deltas, so a collection mid-run cannot hide anything. Each
accessor bound to its own configuration's index, 100,000 documents, reading path `status`.

| | solution A | **variant-enc** | ratio |
|---|---|---|---|
| allocated binding the segment | 3,808 B | **27,415,808 B** | 7,200× more |
| time binding the segment | 0.02 ms | **21.62 ms** | 1,000× more |
| **allocated per document read** | **262,801 B** | **491 B** | **535× less** |
| latency per document read | 105,079 ns | **503 ns** | **209× faster** |
| over a 1,000,000-document scan | **262 GB** | **0.49 GB** | 535× less |

Solution A allocates **262 KB to extract one `long` from a 2,846-byte document** — 92× the document's own size. Beyond
"decompress a stored-fields block, parse the document into a map", that figure is not further attributed; it is reported as
measured.

The 105,079 ns/doc probe figure agrees with the filtered server queries (Q2 111.1, Q3 109.5 µs/doc) and is ~2.9× the
sequential Q1 (36.7 µs/doc), consistent with concurrent segment search partitioning the segment.

**GC over the query phase**, from the node's own collector counters:

| | young collections | young GC time | heap at phase end |
|---|---|---|---|
| solution A | **1,264** | **4,253 ms** | 3.33 GB |
| variant-enc | **11** | **194 ms** | 5.54 GB |

115× fewer collections and 22× less GC time. Note what this does **not** say: 4,253 ms of pause against 454 s of query time
is under 1%, so **GC pauses are not why solution A is slow**. The 262 GB of allocation per scan is CPU work regardless of
whether it causes a pause.

variant-enc's higher end-of-phase heap is not retention — it is uncollected garbage in a heap that barely needed collecting.
The real retention figure is the measured one below.

### 6.5 The blob column's one unbounded cost

The reader holds every distinct key name in the segment in memory, per accessor, per segment. Nothing caps it, and this
corpus is the first with a vocabulary large enough to make it visible.

| vocabulary | binding the segment | resident | per name |
|---|---|---|---|
| 1,007 names (the narrower corpus, §3.1) | 0.38 ms | 66 KB | 65.6 B, 377 ns |
| **761,007 names (this corpus)** | **21.62 ms** | **27.4 MB** | **36.0 B, 28.4 ns** |

Per-name cost improves with scale — fixed overhead amortises and `svc1234.attr_5`-shaped names prefix-share well — but the
total is linear in vocabulary and is paid per accessor:

```
one accessor                        27.4 MB,   21.6 ms
five aggregations on one field      137 MB,    108 ms
ten segments x five aggregations    1.37 GB
```

**This is visible in two of the results above.** Q10 regressed to 2.8× slower than `_source`, because the 21.62 ms bind *is*
the whole query. Q8 (five aggregations) gets 103× where Q1 gets 206× — five accessors build five name tables.

Extrapolating the same shape to 10 million distinct names gives ~360 MB per accessor. There is no cap and no fallback: the
reader would attempt it. A field whose keys embed an identifier (`{"tenant_a1b2c3.latency": …}`) has exactly that
vocabulary, and `flat_object` exists partly so such data does not explode the mapping — so being pointed at such data should
be expected.

Three fixes, none free:

1. **Share the table per field per segment** across accessors. Removes the multiplier on Q8 and on concurrent queries; does
   not reduce the 27.4 MB. Unambiguously worth doing.
2. **Cap it and resolve names per lookup instead.** Bounds memory, at a cliff: resolving a name in scattered order measures
   ~14,000 ns against ~28 ns amortised in a sequential sweep, because Lucene stores sorted terms in compressed blocks of 16.
3. **Build it lazily**, in vocabulary order, only as far as a query needs. Helps small queries like Q10; does nothing for
   scans.

This round establishes the cost of *having* the table. It does not measure the cost of not having it, which is what 2 and 3
need before either is chosen.

## 7. Corrections

Recorded because each was stated before it was measured.

| claim | status |
|---|---|
| "at ~100 attributes/doc the index will be 250–400 GB per configuration, so 10M documents is infeasible" | **Wrong by 60×, my arithmetic.** I extrapolated from 1,000 attributes per document rather than the 100 specified, then applied it to 10M documents. The actual index is 5.2 GB per configuration at 1M documents; 10M would have been ~52 GB. Disk was never the constraint — solution A's 235 s group-by was. |
| "solution A is slow here because of GC from parsing 100-entry maps" | **Refuted by the collector counters.** Young GC over the whole query phase is 4,253 ms against 454 s of query time, under 1%. Allocation volume (262 GB per scan) is real work but it is not pause time, and I asserted the mechanism before reading the counters. |
| "the storage advantage should hold around −4.6%" | **It did not: −2.07%.** Not because the blob got worse but because `.tim` grew five-fold and dilutes the margin. I had identified that dilution as a risk before the run and then still framed the expectation on the old figure. |
| "the name table is a fixed per-segment cost" | **Misleading as written.** Fixed with respect to document count and to how many distinct key *combinations* exist — but linear in vocabulary, which no earlier measurement had moved. 66 KB became 27.4 MB. |

## 8. Limits

- **n=5, not 10.** p90 here is the 5th of 5 values and is not a tail estimate.
- **One million documents, one segment.** The name table's per-document share falls as segments grow, so this is the
  *pessimistic* end for variant-enc on the memory axis; a 10M-document segment would amortise 27.4 MB ten times better.
- **Concurrent segment search was on.** Both configurations get it equally, so the comparison holds, but absolute
  per-document figures are wall-clock across slices and are not directly comparable to the single-threaded probe numbers.
- **Vocabulary was moved once, not swept.** 1,007 → 761,007 shows the cost is linear and material. It does not locate the
  point at which a cap becomes necessary.
- **Solution A is not optimised**, by decision. Its 262 KB/doc of allocation looks like it has headroom; narrowing it would
  reduce the gap and is not evaluated here.
- **Working sets larger than RAM are untested.** This index fits in page cache alongside the heap.
- **One `flat_object` field, one shard, single-threaded client.** Multi-field and concurrency costs untested.
